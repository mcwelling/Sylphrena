Getting the right toolchain into the container

Research notes for discussion · 28 November 2026 · written against phase6-subagents (3a35935)

Syl runs every project in one Rust-flavoured image. Other tools solve this problem in roughly six ways, and the "build a minimal image on demand" idea is one of them. That approach is sound, and the tools for it already exist. The hard parts are elsewhere: working out what a project needs, and handling the toolchain the agent discovers it needs halfway through a session. Assembling the image is the easy part.

1. What Syl does today

In crates/syl-container/src/lib.rs, the first cold start does the following:

  1. Starts from mcr.microsoft.com/devcontainers/base:ubuntu.
  2. Runs SETUP_TOOLS_CMD, which runs apt-get (python3, ripgrep, jq, build-essential, libssl-dev, …), downloads yq, and runs rustup stable.
  3. Runs podman commit to save the result as syl-agent-ready:latest, which every later start reuses.

Problems with this, roughly from most to least important:

  • One image for every project. A Node 20 + pnpm project, a Python 3.11 project and a Go project all get the same Rust stable toolchain and nothing else. When the agent installs what's missing with apt or curl during a session, those installs live only in that container and are lost on --fresh or a rebuild.
  • The image is not reproducible. podman commit captures whatever state the container was in, and nothing records how it was produced. "stable" and latest mean different things on different days.
  • The architecture is hard-coded. yq_linux_amd64 is downloaded even on Apple Silicon, where Podman's VM is arm64. It's a small bug, but it shows that any composer has to handle more than one architecture from day one.
  • Network-off mode can't do a first start. That's already reported as an error, but it's the same problem: setup is imperative and network-bound.

2. How others solve it

The approaches fall into six groups. Most real systems combine two of them.

ApproachExamplesHow it worksGood atWeak at
A. One large image plus a setup script Codex cloud (codex-universal), Claude Code on the web, Codespaces' default image A large shared image with many languages already installed. Versions are picked with environment variables (CODEX_ENV_*), and a per-repo setup script adds the rest. Codex caches the container after setup and throws the cache away when the script, variables or secrets change. Works for most repos with no configuration. Only one image to maintain. Several GB on disk. Version pinning only covers what the image's authors anticipated.
B. A declarative spec built into an image Dev Containers (devcontainer.json plus Features), Coder envbuilder, OpenHands runtime images The repo declares a base image and Features (tarballs with install.sh, distributed as OCI artifacts, installed in a set order). A builder turns that into an image. OpenHands tags each image with a hash of its base image and dependency lock files, and checks the most specific tag first, then the more general ones, before building. An existing standard that many repos already ship. Builds are cached by content hash. Features are arbitrary shell scripts. The Dev Containers CLI assumes Docker semantics.
C. Detect from the repo, then build Railpack (successor to Nixpacks), repo2docker (Binder) Detectors look for files such as package.json, requirements.txt or go.mod and produce a build plan. Railpack gets runtime versions from mise and builds with BuildKit. repo2docker splits installs into separate steps so layers cache well. Needs no configuration for common stacks. Built to produce deployable apps, not development environments. Struggles with uncommon cases such as native libraries and monorepos.
D. Build images from packages, with no RUN steps Nix dockerTools / nix2container, Chainguard apko (Wolfi), mise oci build (experimental), flox containerize, Devbox The image is assembled directly from a package list. Nothing runs inside it while it's built. mise oci build puts one layer per tool, so changing one version rebuilds only that tool's layer. nix2container skips layers that already exist. Reproducible, cacheable at a fine grain, and nothing from the project runs at build time. This is the user's idea, and it's already implemented several times. Only works within one consistent package set (apko can't mix Wolfi and Alpine packages). Nix has a steep learning curve. mise oci is still experimental.
E. A version manager inside a general container mise / asdf, devbox shell, a Dev Container with a mise Feature Keep the image generic, and install the versions the repo asks for (mise.toml, .tool-versions, .nvmrc, .python-version) into a cache directory at startup. Installs are symlinks into a shared download cache. No image rebuilds. Mid-session changes take seconds. One cache can be shared by every project. Covers language runtimes, not system libraries like libpq-dev, protoc or libvips.
F. The agent sets up its own environment EnvBench, SetupBench, ExecutionAgent, SWE-Factory, Repo2Run An LLM reads the repo, installs things, runs the build and tests, and repairs failures from the errors. The long tail that no detector covers. Unreliable. EnvBench: the best agent fully set up 29% of JVM repos and 7% of Python repos. SetupBench: 38–57% on repo setup, with 38–89% of actions unnecessary. It works much better when error feedback is part of the loop.

Podman detail worth knowing: --mount type=image,source=…,destination=… mounts one image's filesystem into another container, read-only by default according to one tutorial (check on our Podman version). That would let a toolchain image be attached to the agent container without merging layers.

3. Testing the "build minimal images on demand" idea

As I understand the proposal: a separate CLI reads a project's needs, builds a minimal image, and hands it over. Bondsmith orchestrates it, or Syl calls it when running alone. No registry is needed, because an image is only a tarball.

What holds up

  • Declarative and keyed by hash is the right shape. OpenHands, Codex and envbuilder have all converged on "a hash of the inputs is the image tag; rebuild only when it changes." Doing the same replaces podman commit with something reproducible.
  • No registry is right for solo use. Podman's local image store is the cache. A registry only matters for sharing between machines or a team, and that can be added later.
  • Making it reusable is right. It matches the existing decision that syl-container is shared, so Bondsmith can run agents that have no sandbox of their own in the same environments.

Hole 1: "an image is just a tarball" is true of the format, not of what goes in it

Layers stack cleanly only when every binary in them agrees on the C library, the filesystem layout and the dynamic linker. That's why apko won't mix Wolfi and Alpine packages, and why Nix works: each store path carries its own dependencies. A composer therefore needs one consistent package set. The realistic options are Nix, Wolfi apk, Debian apt, or the relocatable toolchain tarballs that mise downloads (Node, Go, Rust, JDK, python-build-standalone). Writing the tarball assembler ourselves is the least valuable part. buildah (Podman-native and scriptable), mise oci build and nix2container all do it already.

Hole 2: working out what to install is the hard part

Version files cover runtimes: rust-toolchain.toml, .nvmrc, go.mod's go line, .python-version, mise.toml. They don't cover the system libraries a build pulls in, such as openssl-sys needing libssl-dev, a Python wheel needing a compiler, or a test suite expecting Postgres. Detectors handle the common cases, and the benchmarks show that even agents fail on the rest. Any design needs (a) a written spec a person or agent can edit, and (b) a way to check it, by running the project's build or test command.

Hole 3: "minimal" works against what an agent needs

An agent needs a development environment: compilers, headers, git, ripgrep, a debugger, a shell, and Syl's own tools. A minimal runtime image lacks those. Separate minimal images per project also cost more disk than one shared base plus small per-project layers, because layers are only shared when their digests match. In practice the efficient shape is a shared development base plus thin, per-project toolchain layers. That's mostly what group D tools produce when you give them a fixed base.

Hole 4: needs change mid-session

The agent finds out it needs protoc after twenty minutes of work. A design where images only change at build time means rebuilding and restarting a container that several sessions share (one per project, per Phase 4). There needs to be an immediate path, installing into the running container or a cache volume, whose result is written back into the spec. The next build then picks it up instead of losing it.

Hole 5: a cloned repo's spec decides what gets installed

This is the same trust problem as hooks and MCP servers. A devcontainer.json Feature or a Railpack plan runs arbitrary shell during the build. Two rules follow: builds run inside the container or VM, never on the host, and anything beyond a pinned package list (any script) goes through the existing trust prompt. A purely declarative spec (packages and versions, with checksums) is the safe default, and that favours groups D and E.

Hole 6: a separate CLI is one more thing to install and version

A separate CLI isn't wrong, but it doesn't have to be a separate project. A second binary in this workspace, built on syl-container (for example syl-env, or syl env build), gives Bondsmith something to call and Syl something to link against, with one release process. Split it out only if a non-Syl user turns up.

4. What I'd suggest, for discussion

  1. A shared base image, built from a checked-in Containerfile instead of podman commit. It has Syl's agent tools, build-essential, python3 and mise, but no Rust. Tag it with a hash of the Containerfile, and build it for both arm64 and amd64. This alone fixes reproducibility and the yq bug.
  2. Runtimes from the project's own version files, through mise. Read the files that already exist (rust-toolchain.toml, .nvmrc, .python-version, .tool-versions, mise.toml, the go line in go.mod). Install into a named Podman volume shared by every project, so Node 20 is downloaded once per machine, not once per project. No image rebuild is needed, and mid-session changes are a mise use away.
  3. System packages from a small spec, such as an [env] section in .syl/config.toml listing apt packages. Build them as one thin layer on top of the base with buildah, tagged with hash(base digest, spec, arch), the way OpenHands does it. When a repo already has devcontainer.json, use it: its image as the base, and its Features behind the trust prompt. That follows the "standards before inventing formats" principle.
  4. Agent-assisted setup as the fallback, not the first resort. When the build or test command fails for an environment reason, a setup subagent (Phase 6 makes this cheap) proposes spec changes, checks them against the build command, and the result is written to the spec for review, not left inside the container.
  5. Bondsmith's role: show the resolved environment per project, let people edit the spec, run builds in the background, and share the base image and mise volume across every agent it hosts.

The second step might solve 80% of the problem for little work, so it's the one I'd prototype first. Nix (via flake.nix or Devbox) is worth supporting as an opt-in when a repo already uses it, but I wouldn't make it the default.

5. Questions to settle

  1. Spec format: an [env] section in Syl's own config, devcontainer.json only, or both, with devcontainer.json taking precedence when present?
  2. Runtime installs: into a shared mise volume (fast, can change mid-session), or baked into per-project layers (fully reproducible, slower to change)? I lean towards the volume, with an option to bake.
  3. Packaging: a subcommand or a second binary in this workspace, or a standalone project?
  4. Which distribution the base uses: stay on the Ubuntu devcontainers base (works with Features, large), or move to Debian slim or Wolfi (smaller, but Features are less certain to work)?
  5. Whether the agent may change the environment on its own, or only propose spec changes for approval.

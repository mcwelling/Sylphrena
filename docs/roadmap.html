Syl Roadmap: from harness to Bondsmith

November 2026 · written against remove-bedrock (eb09481)

Syl is a solid single-user terminal agent with one strong opinion: everything the model runs happens inside a Podman container. The open-source harnesses surveyed here have moved past “a REPL around a tool loop” in three directions:

  1. A headless core with a protocol in front of it. The TUI becomes one client among several.
  2. Durable, append-only session logs. These make branching, undo, resume and replay cheap.
  3. Extensibility through shared standards. That means MCP, Agent Skills, AGENTS.md and ACP, not bespoke formats.

Bondsmith is a meta-harness desktop app, so the most important item on this roadmap is Phase 4: Syl must speak ACP (Agent Client Protocol). Goose, CodeWhale and DeepSeek Harness already do, and Zed and JetBrains use it as their agent interface. If Bondsmith is an ACP client, it can host Syl, and it can host other agents the same way. Everything before that phase is groundwork that makes Syl worth hosting.

1. Where Syl stands today

Strengths worth keeping

Container-first sandboxEvery command runs in a per-project Podman container. .syl/ is mounted read-only, and ~/.ssh is read-only. Most harnesses either have no sandbox (pi) or bolt on Seatbelt/bubblewrap (CodeWhale, Codex). This is Syl’s main differentiator.
Single Rust binaryFast startup and no Node or Python runtime. Goose and CodeWhale make the same bet.
Prompt-cache disciplineFrozen system prompt, append-only history and thinking-block handling are already correct for Opus 5.5.
Persona and memoryPersistent markdown memories are injected at conversation start. The persona gives Syl character.
WorkflowsMarkdown pipelines run with /workflow. These are a seed for something recipe-like.
Cost and TPM trackingLive cost and rate-limit bars.

2. Field survey: ideas worth taking

pi

Mario Zechner · pi-mono / pi.dev · TypeScript · minimal core, maximal extension
  • Four default tools (read, write, edit, bash) and a deliberately tiny system prompt.
  • Sessions are JSONL trees. Each entry has an id and parentId, so /tree, /fork and /clone branch inside one file, and side quests can be summarized back into the main line.
  • TypeScript extensions can register tools, commands, providers and tool_call hooks, and draw TUI widgets and overlays. /reload hot-reloads them. Plan mode, subagents, permission gates and MCP all ship as extensions, not core.
  • Skills follow the Agent Skills standard (SKILL.md). Prompt templates expand with /name, and both can be bundled as installable packages (npm/git).
  • Modes: interactive, -p print, --mode json (event stream), --mode rpc (JSONL over stdio), and an SDK. OpenClaw is built on the SDK.
  • Steering queue: Enter queues a message for after the current tool calls, and Alt+Enter queues one for after all work is done.
  • Opinions: no MCP (tool schemas load at session start and break the cache on reload), no built-in todos, no permission popups (use a container).

opencode

sst / anomalyco · TypeScript on Bun · client/server first
  • One server process hosts the runtime, and the TUI, desktop app and web pairing are all clients. An OpenAPI 3.1 HTTP API covers sessions, prompts, interrupt, compact, fork, revert, per-turn diffs, permissions and an event stream (session.text.delta, permission.asked, …).
  • Agents: primary agents build and plan (edits denied), and subagents general and explore. Agents are markdown files with frontmatter. Subagents run in child sessions with fresh context, and the depth limit defaults to 1.
  • Permissions: an ordered list of {action, resource, effect} rules with allow/ask/deny; the last match wins and the default is ask. A shell scanner checks subcommands separately. Approvals can be once, always or reject, and managed policies override the project.
  • Two-step revert (stage, then commit) over filesystem snapshots. LSP servers and formatters run after edits.
  • Compaction is token-based (keep.tokens, and a buffer of free context reserved before auto-compaction).
  • MCP: stdio and Streamable HTTP with OAuth, server instructions injected into the prompt, elicitation rendered as forms, and “Code Mode” (MCP tools exposed as one JavaScript API).

Goose

Block, now Agentic AI Foundation · Rust + Electron · ACP, recipes
  • A Rust workspace (core, CLI, server) plus an Electron desktop app that talks to its backend over ACP. goose acp serves ACP over stdio, and goose serve over HTTP/WebSocket with a secret key.
  • Extensions are MCP servers (built-in, stdio, remote). MCP Apps render interactive UIs in the desktop app.
  • Recipes are YAML files with instructions, a prompt, extensions, settings, {{ parameters }}, retries with shell checks, a json_schema structured response and sub-recipes. They can be shared, deep-linked and run on a cron schedule.
  • Subagents come from the summon extension. They run sequentially or in parallel (up to 5), have turn and time limits, and can’t spawn further subagents.
  • Adversary mode: a reviewer model sees the task and each shell call and returns ALLOW or BLOCK. It fails open.

DeepSeek Harness (dsh)

deepseek-ai · TypeScript/Node · everything is a plugin
  • Runtime with web, headless, SDK and ACP profiles, plus an Electron app. The model adapter, tool registry, session log and agent loop itself are swappable plugins.
  • “Model-visible means logged”: every model request can be rebuilt from the append-only, versioned session log (session.vN.jsonl, with migrations). History is derived from the log rather than stored separately.
  • Sandbox seam: every spawn goes through a sandbox backend, and approval policy is a plugin. Subagents, a shared task board (“Agent Teams”) and turn-boundary forks are also included.

CodeWhale and Whale

CodeWhale: Rust, ex-deepseek-tui · Whale: Go, now archived
  • Modes: Plan (read-only), Work, and Operate (runs until the goal is verified). Permission levels are Ask, Auto-Review (a reviewer model approves routine calls) and Full Access.
  • OS sandbox: Seatbelt on macOS, bubblewrap on Linux. Inside it, the shell can’t read ~/.ssh, ~/.aws or .env.
  • Receipts (/receipts) record every changed file, command, web or MCP call, subagent and approval. /undo reverts the last request, and /restore rolls back to a snapshot.
  • Claude Code compatibility, opt-in: it can import CLAUDE.md, settings, MCP config and skill/command plugins.
  • Front ends: exec, web, review --pr N, app-server --http and serve --acp.
  • Whale claimed very high prompt-cache hit rates from aggressive context reuse. It published no mechanism.

Others

From prior knowledge, not re-checked here
  • Codex CLI (Rust): OS sandboxing (Seatbelt/Landlock), an apply_patch edit tool, AGENTS.md, and an app-server JSON-RPC protocol.
  • Claude Code: hooks, skills, subagents, plugins, MCP and checkpoints.
  • Aider: repo maps and git-commit-per-edit.

4. Principles for Syl

  1. The container is the sandbox and the selling point. Build permissions, undo and receipts around the container rather than replacing it. Keep “runs everything in Podman” as the default experience, unlike pi and opencode.
  2. The core is a library; the TUI is a client. Every feature lands in the core and is exposed as events or commands. The TUI, -p, ACP and Bondsmith all consume the same stream.
  3. Model-visible means logged (from dsh). The session log is the source of truth. History, resume, fork, undo, receipts and Bondsmith’s timeline are all derived from it.
  4. Use standards before inventing formats. That means AGENTS.md, Agent Skills, MCP and ACP. Syl’s own formats (workflows, memories) should map onto them.
  5. Keep the prompt cache intact. Tool definitions and the system prompt stay frozen within a conversation, as Syl already does. Load skills and MCP instructions in ways that don’t invalidate the cached prefix (this is pi’s critique of MCP).
  6. Stay Anthropic-first, but keep a seam for other providers. One ModelAdapter trait, one implementation, no 80-provider matrix.

5. Roadmap

Each phase ends in something shippable, and most phases unblock the next. Rough sizes assume one developer working with an agent.

PHASE 0

Core extraction

foundation · ~1–2 weeks

The goal is an agent loop that runs without a terminal.

  • Create a syl-core crate (workspace or module) owning the agent loop, tools, sessions, compaction and the API client. main.rs shrinks to the TUI client.
  • Define an AgentEvent stream: TurnStarted, TextDelta, ThinkingDelta, ToolCallStarted{id,name,input}, ToolCallFinished{id,output,is_error}, PermissionRequested, Usage, Compacted, TurnEnded{stop_reason}, Error. Pair it with a command channel: Prompt, Cancel, ApprovePermission, SetModel.
  • Move the TUI onto that stream. It becomes the first client and stops calling into loop internals.
  • Add a ModelAdapter trait around stream_turn/call_with_retry_shared, with only the Anthropic implementation for now.
  • Add end-to-end tests that drive the core with a wiremock model and a fake podman (the pattern from tests/bash_pipes.rs), asserting on events.
Done when: a test runs a full tool-using turn with no TTY, and the TUI behaves exactly as before.
PHASE 1

Session log and context

~1–2 weeks
  • Replace session.json with an append-only JSONL log under .syl/sessions/<id>.jsonl. Entries carry id, parentId, type and a timestamp. Types are messages, tool calls and results, compaction summaries, model switches and approvals. Each line is fsynced.
  • Derive model history from the log (derive_messages). Compaction appends a summary entry instead of rewriting history, so the full transcript survives.
  • Add commands to list sessions, resume (--continue, --resume), fork from an entry and name sessions.
  • Make compaction token-based. Track the context size from usage, compact when within a buffer of the model’s window (for example 15%), and keep the most recent N tokens rather than 10 messages. Also run it when the API reports the context overflowed, then retry.
  • Spill large tool results: store the full output in the log or a file, give the model a preview plus a handle, and let read_file page through it.
Done when: killing Syl mid-turn loses nothing, and syl --resume / /fork work.
PHASE 2

Tool parity

~1 week
  • Add edit_file (exact string replace with a uniqueness check) and write_file, both executed in the container. Each returns a unified diff, which also becomes a receipt entry.
  • Add grep (ripgrep in the container), glob and ls. All three are cheap and read-only.
  • Run read-only tool calls (read, grep, glob, ls, memory_read) in parallel. Keep run_bash and edits sequential.
  • Load AGENTS.md (and CLAUDE.md as a fallback) from the project and its parent directories into the frozen system prompt.
  • Accept images in prompts (paste a path or @file). show_image already covers output.
  • Add a steering queue: messages typed while the agent works are delivered after the current tool calls, as in pi.
Done when: the model can work through a multi-file refactor with dedicated tools, and the TUI shows a diff for each edit.
PHASE 3

Control and safety

~2 weeks
  • Permissions: ordered allow/ask/deny rules over {tool, pattern} in .syl/config.toml. The last match wins. run_bash gets a simple command splitter so git status && rm -rf x is checked per command. Approvals can be once, always for this project, or reject. Defaults suit a container: allow everything except network egress and git push (ask), with deny for paths outside /workspace.
  • Checkpoints and undo: before each turn that changes files, snapshot the workspace with a shadow git repository (git --git-dir=.syl/shadow.git --work-tree=/workspace) so the user’s own git history isn’t touched. /undo reverts the last turn, and /restore <n> goes back further. Revert is staged and then committed, as in opencode.
  • Receipts: a /receipts view derived from the log, listing files changed, commands run, URLs fetched and approvals given for each turn.
  • Modes: plan (read-only tools; edits and writing run_bash denied by rule) and build. Toggle with a key and show the mode in the status bar.
  • Optional reviewer: a cheap-model ALLOW/BLOCK check for ask items, so they can be auto-approved (from Goose’s adversary mode and CodeWhale’s Auto-Review). Unlike Goose, it should fail closed.
  • Container hardening: an optional network-off mode (--network=none, with an allowlist proxy later) and per-project resource limits in config.
Done when: rm -rf inside a turn can be undone in one keystroke, and plan mode can’t change files.
PHASE 4

Headless modes and ACP

the Bondsmith seam · ~2 weeks
  • syl -p "prompt" runs one turn and prints the answer. --output json streams AgentEvents as JSONL, which also serves CI and scripting.
  • syl acp runs an ACP agent over stdio supporting initialize, session/new (cwd, mcpServers), session/prompt, session/load, session/cancel, session/request_permission, and session/update notifications (message chunks, tool calls, tool call updates). Map AgentEvent onto it one to one.
  • Run one container per project, shared across sessions, and allow several sessions per process. This is needed once Bondsmith opens more than one tab on a project.
  • Test it against Zed’s ACP client and the ACP SDK’s test harness, so Bondsmith isn’t the first and only client.
  • Later: syl serve with ACP over WebSocket and a shared-secret header, as goose serve does, for a Bondsmith instance on another machine.
Done when: Zed can drive Syl as an external agent, including approvals and cancel.
PHASE 5

Extensibility

~2–3 weeks
  • MCP client: stdio and Streamable HTTP servers configured in .syl/config.toml. Namespace tools as server__tool. Load them when a conversation starts and freeze them with the system prompt to protect the cache. Inject server instructions. Decide whether MCP servers run inside the container (the default, for safety) or on the host (opt-in, for things like browsers).
  • Skills: discover SKILL.md directories in .syl/skills/, ~/.syl/skills/ and .agents/skills/. Put only names and descriptions in the system prompt, and load the full skill on demand, either through a skill tool or /skill:name.
  • Hooks: shell commands configured for pre_tool, post_tool, turn_end and session_start. They get JSON on stdin, and a non-zero exit blocks. This is the simplest extension point and needs no plugin runtime.
  • Workflows become recipes. Keep the markdown format, and add {{params}}, retry-with-check steps, the model and tools to use, and an optional JSON schema for structured output. Workflows that only run commands keep working as they do now.
  • Custom slash commands as prompt templates in .syl/commands/*.md.
  • Hold off on a full plugin runtime (pi-style TypeScript or Wasm) until hooks, MCP and skills prove insufficient.
PHASE 6

Multi-agent

~2 weeks
  • A task tool that runs a subagent in a child session. It gets fresh context, the parent’s container, a restricted toolset (for example read-only explore) and its own turn and token budget, and returns only a summary. The depth limit is 1. Child sessions show up in the log and in ACP as nested sessions.
  • Agent definitions are markdown with frontmatter (description, model, tools, permissions) in .syl/agents/, the shape opencode and Claude Code use.
  • Parallel subagents (bounded, for example at 4) for fan-out research.
  • Make dispatch_agent an explore/fetch subagent instead of a special case.
LATER

Optional

  • LSP diagnostics after edits, run inside the container. These are high value for typed languages.
  • Scheduled recipes (cron), which Bondsmith may own instead of Syl.
  • More providers through the ModelAdapter seam: OpenAI-compatible and local models (Ollama/vLLM) for cheap subagents and compaction.
  • Session export to HTML or markdown, and sharing.
  • Code Mode: the model writes one script that calls several tools (opencode, CodeWhale). Worth trying once MCP is in place, since token savings on tool-heavy tasks can be large.

6. What Bondsmith needs from Syl

If Bondsmith is a meta-harness, its natural shape is an ACP client that hosts many agents. Syl would be the reference agent, with Goose, CodeWhale, Claude Code (via claude-acp) and Codex (via codex-acp) as peers. The contract Syl should meet:

Start, stop and cancel agents in any projectsyl acp + one container per project4
Streamed text, thinking and tool activityAgentEvent → session/update0, 4
Approval UIsession/request_permission backed by the rule engine3, 4
Session list, resume, fork and timelineAppend-only log + session/load1, 4
Diffs, undo and receipts per turnShadow-git checkpoints + receipts derived from the log3
Shared MCP servers across agentssession/new accepts mcpServers4, 5
Cost and usage per agentUsage events0
Several sessions at onceMulti-session core4

Two design questions to settle early

These shape Phases 0–4.

  1. Where does the sandbox live? If Bondsmith hosts agents that have no sandbox of their own (pi, Claude Code), it may want Syl’s container machinery as a shared service (“run any ACP agent inside a Syl container”). That argues for syl-container as a separate crate from the start.
  2. Who owns memory, workflows and schedules: Syl or Bondsmith? If Bondsmith shares them across agents, keep Syl’s formats plain files (they already are) and let Bondsmith read the same .syl/ directory, rather than building Syl-specific APIs for them.
